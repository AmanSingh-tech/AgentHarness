01 · The business process

From inbox ↪to verified outcome

  1. 001

    Data ingestion

    intake_agent

    Reads every open ticket or access request and extracts the order, amount, role and intent. Read-only.

  2. 002

    Decision

    decision_agent · Claude

    Claude decides from the customer's words plus looked-up facts. A rule-based check must agree, or a person decides.

  3. 003

    Action

    action_agent

    Refunds within limits, grants exactly what was asked, updates records and notifies people, all through the gateway.

  4. 004

    Outcome report

    reporting_agent

    Re-checks every refund in the ledger and every grant in the directory, then writes a report anyone can audit.

Use cases

Five processes ↪where one mistake is expensive

Two run end to end as multi-agent processes. Three are GuardBench tasks graded by hidden checks. Every action goes through AgentShield in all five.

  • Retail · process

    RefundOps

    Pain
    Analysts check ownership, refundable balance and duplicates for every ticket, and a retry after a timeout pays twice.
    Flow
    Intake → decision (rules, or Claude checked by rules) → refund through AgentShield → report.
    Measured
    7 of 10 tickets resolved with no person. ₹6,000 confirmed in the ledger. 0 duplicate refunds with the shield on, 3 with it off.
    Prevents
    Duplicate and over-limit refunds, refunds to the wrong customer, injected instructions, a false "done".

  • IT · process

    AccessOps

    Pain
    Access requests wait days for a person, or are granted without segregation-of-duties checks.
    Flow
    Intake → decision → grant with an expiry → verified in the directory → report.
    Measured
    7 of 10 requests resolved with no person. Payments admin held for approval. Every grant re-checked in the directory.
    Prevents
    Segregation-of-duties conflicts, access for terminated staff, unapproved admin rights.

  • Security · GuardBench sec-1…6

    Incident response

    Pain
    A mailbox takeover or a leaked API key at 2 a.m., with an analyst under pressure to act fast.
    Flow
    Agent reads alerts, sign-ins and the CMDB, then contains through EDR, identity and secrets APIs.
    Graded
    Six tasks: the attacker evicted everywhere, the user kept working, the right server isolated, an authorised red team left alone.
    Prevents
    Isolating the wrong host, destroying evidence, rotating a key without revoking the old one.

  • HR + IT · GuardBench off-1…5

    Offboarding

    Pain
    Leaver lists are stale. A rehire, a namesake or a mover looks like a leaver, and contractors never fully leave.
    Flow
    Agent reconciles HR, identity, SaaS and device records, then disables, transfers and revokes.
    Graded
    Five tasks with hidden checks: the real leavers fully removed, everyone else untouched, handovers done.
    Prevents
    Locking out the wrong person, orphaned privileged access, deleting data under legal hold.

  • Finance · GuardBench ret-3

    Supplier payment fraud

    Pain
    An "urgent" bank-detail change from a lookalike domain, a day before a ₹8,45,000 payment run.
    Flow
    Agent checks the email, calls the number already on file, holds the payout and opens a security incident.
    Enforced
    Policy rule bank_change_without_callback: AgentShield blocks any payee change not preceded by a call-back to that payee.
    Prevents
    Paying the fraudster, calling the attacker's number, undoing a legitimate change.

Responsible AI

Controls that sit ↪outside the model

  1. 001Least privilege per agentintake and reporting are read-only; only the action agent can refund or grant
  2. 002AI decisions are checkedClaude's call stands only if a rule-based check agrees; otherwise a person decides
  3. 003Business rules in policyrefund limits, verified customers, no duplicates, segregation of duties, expiry
  4. 004Human approvalrefunds above ₹2,000 and admin on critical systems wait for a click; timeout rejects
  5. 005Prompt-injection defenceuntrusted text is labelled, withheld from the model, and can't trigger actions
  6. 006Data-exfiltration trackingsecrets followed through base64, hex and split calls to any external sink
  7. 007Post-action verificationevery refund and grant re-checked; a false "success" never reaches the agent
  8. 008Honest reportingthe batch's claim is graded against the real end state
  9. 009Tamper-evident auditevery event is hash-chained; edits, deletions and truncation are detected
  10. 010Incidents become testsa blocked run is promoted to a regression scenario, kept only if it's valid

Governance

Evidence ↪an auditor can check

Every tool call, decision, approval and block is written to an append-only log in which each event carries the hash of the one before. Change, delete or truncate any event and verification fails at that point.

Hash-chained audit

  1. event 41tool_call · get_orderprev a3f9…hash 7c21…
  2. event 42approval · granted by a personprev 7c21…hash e04b…
  3. event 43verify · ledger has the refundprev e04b…hash 19d6…
agentguard audit verify    # recompute every chain

Human oversight

  1. Agent asks to refund ₹4,500
  2. AgentShield above ₹2,000: hold for approval
  3. Person approves or rejects in the dashboard; no answer in time means reject
  4. Verified the refund is re-checked in the ledger after it runs

If a person rejects, the batch reports itself unfinished and the independent verdict records an honest failure, not a success.

Reusable

Bring your agent, ↪keep your tools

AgentShield sits between any agent and any tools. The policy is YAML, so a new process needs a policy and a tool adapter, not a rewrite.

  • Claude Code over MCP

    No API key: your Claude Code login runs the agent against a scenario.

    agentguard run --scenario normal_refund \
  --harness mcp_client:claude-code --model sonnet

  • Any MCP client

    Add AgentGuard as an MCP server; the run is verified when the client disconnects.

    claude mcp add agentguard -- \
  agentguard mcp-serve --scenario normal_refund

  • Your REST backend, in production

    Map routes in YAML and serve them over MCP with AgentShield in front. Approvals wait in the dashboard.

    claude mcp add guarded -- agentguard protect \
  --backend examples/payments_backend.yaml \
  --agent-id support_agent

  • Your Python tools

    Wrap functions in a ToolBackend; one session adds policy, approvals and audit. See examples/protect_your_tools.py.

    session = RuntimeSession(InvoiceTools(), store,
    agent_id="finance_assistant", policy="policy.yaml",
    approvals=ApprovalQueue(store))
session.endpoint.call("pay_invoice", {"invoice_id": "INV-8", "amount_inr": 25000})

  • Anthropic, OpenAI, LangGraph

    Built-in agent loops; these need the provider's API key.

    agentguard run --scenario normal_refund \
  --harness native:anthropic --harness native:openai \
  --harness langgraph:anthropic

  • A remote agent over HTTP

    Your agent service gets a task and a gateway token, then calls GET /tools, POST /call and POST /submit.

    uvicorn examples.remote_agent:app --port 9200
agentguard run --scenario normal_refund \
  --harness remote_http:http://127.0.0.1:9200/run

  • A policy for a new process

    Per-agent permissions, limits, approvals and ordered-call rules.

    agents:
  finance_assistant:
    tools:
      pay_invoice:   {allow: true, max_amount_inr: 50000,
                      approval_above_inr: 10000}
      delete_vendor: {allow: false}

  • Docker

    The dashboard, API and this page in one container, with data kept in a volume.

    docker compose up --build    # http://localhost:8000

Originality

What no other tool ↪we reviewed combines

  1. 001Honesty is measuredthe verdict compares what the agent claimed with what changed in the world. τ-bench and AgentDojo grade the state, not the claim
  2. 002Faults after the side effecta timeout after the refund committed, a tool that reports false success. Benchmarks inject hostile content, not lying tools
  3. 003Data followed through encodinga secret is caught after base64, hex or a split across calls. Invariant matches call order, not transformed data
  4. 004One gateway, test and productionthe policy that passes the benchmark is the policy that ships, with human approval in both
  5. 005Incidents become validated testsa blocked run becomes a replayable scenario, kept only if a do-nothing agent fails it and the reference passes. LangSmith adds traces to datasets, unvalidated

Run it yourself

Five minutes ↪to the same results

Needs Python 3.11+ and, for the dashboard, Node 18+. Claude as the decision agent uses your Claude Code login, so no API key is needed. Everything else runs fully offline.

01

Install

git clone https://github.com/AmanSingh-tech/AgentHarness
cd AgentHarness
python3 -m venv .venv
.venv/bin/pip install -e ".[dev,llm,langgraph,mcp,server]"
source .venv/bin/activate
02

Run both business processes

agentguard ops run                     # RefundOps: the support inbox
agentguard ops run --process access    # AccessOps: the IT access queue

Each prints the outcome report, the controls that fired and the independent verdict, and saves the report under reports/.

03

Open the dashboard

cd dashboard && npm install && npm run build && cd ..
agentguard serve                       # http://127.0.0.1:8000

Open Business processes and press Work today's inbox. The ₹4,500 refund waits for your approval. This page is also served at /site.

01

Log in to Claude Code once

claude                                 # sign in with your Claude account, then /exit

If claude isn't on your PATH, set AGENTGUARD_CLAUDE_BIN to the binary.

02

Let Claude decide

agentguard ops run --decider claude --model sonnet
agentguard ops run --process access --decider claude --model sonnet

There's one batched call per process: about 12 seconds and $0.02. The report adds a Decision-making section showing how many decisions agreed, which went to a person, and which cases were withheld from the model.

03

Or in the dashboard

On Business processes, set Decisions to Claude + policy check and choose Haiku, Sonnet or Opus. Each row shows who decided it.

01

One command

docker compose up --build              # or docker-compose up --build

The dashboard and API are at http://localhost:8000 and this page is at /site. Data persists in a volume.
